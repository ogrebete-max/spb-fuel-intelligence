# Свой сервер клуба

## Зачем он нужен

Телефоны в России без VPN не достают до Cloudflare: провайдеры блокируют его адреса. А вход в клуб, отметки и уведомления шли через воркер на Cloudflare. Поэтому клуб переезжает на свой сервер — недорогой VPS в России.

На сервере работает тот же файл [`worker/spbfi-reports.js`](../worker/spbfi-reports.js), что и на Cloudflare, только под Node. Данные клуба лежат в одном файле SQLite. Сайт остаётся на GitHub Pages: после переезда в нём меняется только адрес сервера в `web/config.js`.

## Что где работает

Путь запроса: телефон → `https://<IP>` → Caddy → `127.0.0.1:8787` → `server/main.mjs` → воркер → SQLite.

| Что | Где |
|---|---|
| Код клуба | `/opt/spbfi-club/releases/<версия>`; работающая версия — ссылка `/opt/spbfi-club/current` |
| База | `/var/lib/spbfi/club.sqlite` (рядом служебные `club.sqlite-wal` и `club.sqlite-shm`) |
| Копии базы | `/var/lib/spbfi/backups` |
| Настройки и хеши секретов | `/etc/spbfi/env`, читает только root |
| Node 24.21.0 | `/opt/node-v24.21.0-linux-x64`, ссылка `/usr/local/bin/node` |
| Caddy 2.11.4 | `/usr/local/bin/caddy`, настройки `/etc/caddy/Caddyfile`, сертификаты в `/var/lib/caddy` |

- **Пользователи.** `spbfi` — сервер клуба, `caddy` — Caddy. Войти под ними нельзя, у каждого только свои папки.
- **Порты.** Снаружи открыты только SSH, 80 и 443. Сервер клуба слушает `127.0.0.1:8787`, снаружи до него не достучаться.
- **Caddy** принимает HTTPS, сам получает и продлевает сертификат, сжимает ответы, не пропускает запросы больше 1 МБ и передаёт остальное серверу клуба. HTTP/3 выключен: в российских сетях его часто режут.
- **Службы systemd:** `caddy`, `spbfi-club` (сервер клуба, при сбое перезапускается сам), `spbfi-backup.timer` с `spbfi-backup` (ночная копия базы).
- **Если что-то не так:** `systemctl status spbfi-club` и `journalctl -u spbfi-club -n 100`.

В репозитории всё это — папка [`server/`](../server): `main.mjs` (сервер), `http.mjs` (превращает запросы Node в запросы воркера), `sqlite-d1.mjs` (база), `backup.mjs`, `import.mjs`, `migrate.mjs`, скрипты `*.sh`, Caddyfile и службы. Проверка: `node server/server.test.mjs`.

## Первая настройка

1. **Владелец арендует VPS** в России: Ubuntu 24.04, x86_64, от 1 ГБ памяти. При создании сервера добавляет открытый SSH-ключ мейнтейнера (`spbfi_club_ed25519.pub`) и присылает IP-адрес. Пароль root присылать не нужно, домен не нужен.
2. **Мейнтейнер кладёт загрузки** в `~/.spbfi-club/downloads`: `node-v24.21.0-linux-x64.tar.xz` и `node-v24.21.0-SHASUMS256.txt` с nodejs.org, `caddy_2.11.4_linux_amd64.tar.gz` и `caddy_2.11.4_checksums.txt` из релиза Caddy на GitHub. Установщик сверяет контрольные суммы.
3. **Настраивает сервер** — из репозитория, в Git Bash:
   ```bash
   server/remote.sh setup <IP>
   ```
   Команда ставит Node и Caddy, заводит пользователей и папки, включает службы, файрвол и вход только по ключу. Повторный запуск ничего не ломает.
4. **Выкладывает код:**
   ```bash
   server/remote.sh deploy <IP>
   ```
5. **Проверяет:** `server/remote.sh status <IP>` и в браузере `https://<IP>/club/health`. Первый сертификат Caddy получает за минуту-другую.

Пока данные не перенесены, клуба на новом сервере нет: `/club/health` показывает `"mode":"off"`.

## Перенос данных

Команды миграции старый воркер выполняет только с подписью ключа `~/.ssh/spbfi_migrate_ed25519.pem`, который лежит на ПК мейнтейнера. Ключ владельца и другие секреты со старого сервера не уходят: воркер отдаёт только промежуточный результат хеширования, ПК досчитывает хеш, а новый сервер хранит лишь хеш.

**Проба.** Клуб на Cloudflare всё это время работает как обычно.
1. `node server/migrate.mjs export https://spbfi-reports.ogrebete.workers.dev C:\spbfi-move` — в папке появятся `export.json` (участники, приглашения, отметки, подписки на уведомления, ключи) и `club.env` (настройки и хеши). На экран выводятся только число документов и имена, без значений.
2. `server/remote.sh data <IP> /c/spbfi-move` — загружает на сервер. Перед загрузкой сервер копирует свою базу в `club-before-import-….sqlite`, после загрузки файлы стираются.
3. Проверить:
   - загрузка напечатала `vapid: present` и `club:secret: present`. Без первого уведомления не дойдут до уже подписанных телефонов, без второго перестанут работать пропуска участников;
   - `https://<IP>/club/health` показывает `"storage":"sqlite"` и тот же `"mode"`, что у Cloudflare;
   - `https://<IP>/vapid` отдаёт тот же `publicKey`, что и `https://spbfi-reports.ogrebete.workers.dev/vapid`.

**Переключение** — одним заходом, лучше ночью.
1. `node server/migrate.mjs freeze https://spbfi-reports.ogrebete.workers.dev` — старый сервер перестаёт принимать изменения, и после выгрузки там ничего не запишется.
2. `node server/migrate.mjs export https://spbfi-reports.ogrebete.workers.dev C:\spbfi-move` — ещё раз; в сводке должно быть `frozen: yes`.
3. `server/remote.sh data <IP> /c/spbfi-move`.
4. В `web/config.js` заменить `https://spbfi-reports.ogrebete.workers.dev` на `https://<IP>`, закоммитить и отправить (push). Сайт пересоберётся сам.
5. Проверить на телефоне: владелец и участник в клубе, отметка уходит, уведомление приходит.

**Откат:** `node server/migrate.mjs unfreeze https://spbfi-reports.ogrebete.workers.dev` и вернуть прежний `web/config.js` (revert коммита и push). Отметки, сделанные за это время на новом сервере, останутся только там.

## Обновление кода

```bash
server/remote.sh deploy <IP>
```

Выкладывается закоммиченное состояние `worker/` и `server/`. Если там есть незакоммиченные изменения, команда откажется, пока не добавить `--dirty`. Новая версия ложится рядом с прежними, `activate.sh` переключает на неё `current`, перезапускает сервер и 20 секунд ждёт ответа `/club/health`. Не дождался — возвращает прежнюю версию. Хранятся пять последних версий.

Caddyfile и службы systemd в выкладку не входят: после их изменения нужно ещё раз запустить `server/remote.sh setup <IP>`.

## Копии и восстановление

- Каждую ночь около 03:40 по Москве сервер копирует базу в `/var/lib/spbfi/backups/club-ГГГГ-ММ-ДД.sqlite`. Копия сохраняется, только если прошла проверку целостности. Дневные копии хранятся 14 дней, копии с меткой (например, `club-before-import-…`) — пока их не удалят.
- Копия прямо сейчас: `systemctl start spbfi-backup`.
- Копии лежат на том же сервере: от испорченного файла они спасут, от пропажи сервера — нет. Время от времени стоит забирать свежую копию на ПК:
  `scp -i ~/.ssh/spbfi_club_ed25519 root@<IP>:/var/lib/spbfi/backups/club-2026-09-20.sqlite .`

**Восстановление** — на сервере под root. Сначала сохранить нынешнюю базу под меткой, чтобы не затереть дневную копию:

```bash
runuser -u spbfi -- env SPBFI_DB=/var/lib/spbfi/club.sqlite SPBFI_BACKUPS=/var/lib/spbfi/backups \
  node --disable-warning=ExperimentalWarning /opt/spbfi-club/current/server/backup.mjs --label before-restore
systemctl stop spbfi-club
cd /var/lib/spbfi
rm -f club.sqlite-wal club.sqlite-shm
install -o spbfi -g spbfi -m 600 backups/club-2026-09-20.sqlite club.sqlite
systemctl start spbfi-club
```

Файлы `-wal` и `-shm` удалять обязательно: иначе остатки прежнего журнала наложатся на восстановленную базу.

## Сертификат

- Домена нет, поэтому сертификат выписан на IP-адрес. Let's Encrypt выдаёт такие только краткосрочными, примерно на 6 дней. Caddy продлевает его сам, задолго до конца срока, делать ничего не нужно.
- Срок виден в `server/remote.sh status <IP>`, в строке `notAfter=`.
- Если продлить не удалось (браузер ругается на сертификат), смотреть на сервере `journalctl -u caddy -n 100`. Частые причины: порты 80 и 443 закрыты в панели хостера, у сервера пропал интернет.
- Запасной путь — [acme.sh](https://github.com/acmesh-official/acme.sh) с `--certificate-profile shortlived`: без этого профиля сертификат на IP не выдают. Полученные файлы подключаются в Caddyfile строкой `tls <сертификат> <ключ>` вместо блока `issuer acme`, а продлевает их тогда сам acme.sh.

## Безопасность

- На сервер входят только по SSH-ключу, вход по паролю выключен (`/etc/ssh/sshd_config.d/10-spbfi.conf`). Выключается он, только когда ключ уже добавлен, чтобы никого не запереть.
- Файрвол ufw пропускает только SSH, 80 и 443.
- Сервер клуба работает от пользователя `spbfi` в песочнице systemd: писать может только в `/var/lib/spbfi`, прав администратора у него нет.
- В `/etc/spbfi/env` лежат хеши (`CLUB_OWNER_KEY_HASH` и другие), а не сами ключи, и читает этот файл только root. Даже укравший его не узнает ключ владельца.
- Ключ владельца знает только владелец. Никто не просит его прислать — ни мейнтейнер, ни помощники: для переезда он не нужен.
- Обновления безопасности Ubuntu ставятся сами.
